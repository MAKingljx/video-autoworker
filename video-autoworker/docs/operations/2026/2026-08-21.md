### 耗时

- “总耗时”统一按任务创建到完成计算；未完成任务按创建到当前时间计算，因此视频父任务在最终汇总阶段才写入 `startedAt` 时，不会再把整条任务链误显示为 `< 1 秒`。
- “排队等待”按创建到真实处理开始计算；视频任务的真实处理开始时间取 `prepare`、`audio`、`vision`、`finalize` 媒体子阶段中最早的 `startedAt`。
- “实际处理”按真实处理开始到完成或当前时间计算。缺少可靠处理开始证据时显示 `—`，不伪造耗时。
- 合法的同秒任务仍显示 `< 1 秒`，用于表达时间戳精度内的真实短任务，不再显示错误的 `0 秒`。

# Qwen3.8 视频分析分阶段推理优化

## 需求、规则与生产基线

- 最近 9 个 Qwen3.8 成功视频均为 2220 秒、37 段、111 帧，平均总耗时 `8418.3s`：prepare `10.0s`、Whisper `573.1s`、vision `6475.8s`、finalize `1359.2s`。Qwen 画面与汇总合计占 `93.0%`，阶段时间连续，不是排队或 FFmpeg 瓶颈。
- 同样 2220 秒的 13 个历史 Qwen3.6 任务平均总耗时 `1053s`，其中 vision `337s`、finalize `173s`。Qwen3.8 每个画面请求约 `175s`，Qwen3.6 约 `11.1s`；差异不能只用输出长度解释。

## 根因

- 视频直连请求此前只发送模型、消息、温度和 `max_tokens`，没有发送思考控制；原始 Qwen3.8 chat template 在参数缺失时默认 `enable_thinking=true` 且 `reasoning_effort=xhigh`。37 次画面、8 次章节和 1 次全片请求因此重复执行 46 次深度思考。OpenClaw `second-original=medium` 只约束对话 Agent，没有覆盖这条直连视频链。
- Qwen3.8 视觉运行时是 27B 稠密 BF16、Transformers 5.8.1 + PyTorch 2.12 MPS，RSS 约 90 GB；64 层中 48 层是线性注意力。Apple 节点没有 CUDA `flash-linear-attention` / `causal-conv1d` 快速核，启动日志明确显示退回 Torch 实现。
- Qwen3.6 是约 3B 激活的 MoE、Q8、llama.cpp Metal，并关闭 reasoning。模型激活参数、量化和后端共同造成数量级吞吐差异；仅降低思考无法让 3.8 达到 3.6 的速度。
- 视觉服务使用单请求锁，视频实现又按片段、章节串行 `await`。单个视频不会并行放大显存，但长阶段超过上游等待窗口后，旧 HTTP handler 仍可能继续占用模型，并与下一任务叠加。

## 候选实现

- Qwen3.8 视觉 API 新增受控的 `enable_thinking`、`reasoning_effort` 和安全阶段标签，并返回/记录排队、推理、prompt token、completion token；日志不记录提示词、图片、路径、任务 ID 或结果正文。
- 视频默认改为职责分层：逐分钟画面事实提取 `off / 1536 tokens`，5 分钟章节 `low / 1024 tokens`，全片报告 `medium / 1536 tokens`。最终报告保留一次较完整推理，不在 37 个事实片段上重复深思。
- 三个阶段均可通过独立环境变量覆盖，范围固定为 `off|low|medium|xhigh` 和 `256..4096 tokens`；旧 `AIWORKER_VIDEO_SYNTHESIS_MAX_TOKENS` 继续兼容章节与全片预算。
- checkpoint、同任务恢复、`memoryMode=none`、受控收件箱和结果安全投影保持不变；没有数据库迁移，也不修改模型权重。
