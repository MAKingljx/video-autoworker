## 本地候选改动

- 修复 standalone 工件漏带两项 shell 动态依赖：受管 Markdown 区段渲染 helper 和 OpenClaw 私有 Gateway RPC helper；显式动态闭包收敛为 26 项，并纳入 artifact/manifest 检查。
- standalone 只能从干净 Git payload 构建，必须生成绑定完整 40 位提交与 `<commit>-runtime` release 的 provenance、源码闭包摘要和内容清单；`.PhoenixBrain`、`.run`、数据库、密钥、缓存、日志及其他运行资产均为制品禁入成员。
- 三个 OpenClaw installer 统一复用 shared runtime gate、deployment lock 和 canonical batch root；同一批次必须绑定相同 commit/release，禁止各组件自行生成批次根、并行安装或跨 release 混装。
- 五项安装器高风险路径完成统一收口：锁前 marker/接管同步、失败后的进程树收敛、已验证回滚候选筛选、目标 Gateway fresh restart 合并、component journal 与 terminal handoff 的原子交接。
- 首次 legacy 发布新增唯一 preinstall orchestrator/controller，按 task-flow、video-command、director-brain 的受管顺序安装，只 fresh restart `qwen-current` 一次，再执行 runtime convergence 与 readiness；禁止逐项手工安装或从 bootstrap 绕过 preinstall handoff。
- 生产鉴权统一为 OpenClaw loopback：旧 cookie、API key 和 proxy credential 在该模式下不能提权；幂等、lease、fencing、revision/CAS 与发布锁继续作为一致性门禁保留。
- 视频入口静态审计确认 Telegram/OpenClaw、控制台和 CLI 均汇入唯一 `scheduler-runner -> submit-task -> /api/n8n/trigger`，没有第二套可达派发实现。
- 外部技能目录请求的超时现在覆盖响应正文读取阶段；即使 transport 已返回 header 但 `text()`/`json()` 永不结束，也会在同一有界 deadline 内失败关闭，避免构建或页面请求无限挂起。
- 补强 standalone、蓝绿、导演脑、鉴权、单链和安装器合同测试，覆盖动态 helper、来源闭包、候选 schema、锁/回滚、release 绑定及旧鉴权不可提权行为。
- 正式文档统一首次发布顺序：干净提交构建不可变 standalone，隔离验收，飞书 v2 -> v3 追加迁移，n8n transition/attestation，真实会话工具基线，统一 preinstall orchestrator，legacy controller，blue/green bootstrap，3017 精确切换，最终自然语言与真实视频闭环。
- 统一 preinstall 固定安装 task-flow、video-command、director-brain，只 fresh restart `qwen-current` 一次，再执行 runtime convergence 和 readiness；成功 handoff 后才能进入 bootstrap。失败按 runtime convergence、director-brain、video-command、task-flow 逆序补偿，必要时仅做一次 recovery restart。
- 按飞书决策 `DEC-VAW-DIRECTOR-BRAIN-INTERACTION-001` 收紧 OpenClaw 对话面：公开工具只保留只读 `extraction_status`，从 schema、参数归一化、处理器、Skill 与架构文档中移除 `start_extraction`、`backfill_extraction`；插件侧 loopback 客户端也拒绝任何非状态查询。3017 内部 API、共享应用服务和后台 scheduler 的启动/回填能力继续保留，不新增第二条任务链。
- 导演案例的人工结果门升级为硬合同：候选阶段仍允许缺少“最终使用”“成片位置”“最终效果”，模型提案继续禁止写入三个人工字段；进入“已确认”前必须三项全部由人工填写。历史上状态为已确认但缺少任一项的案例不再视为 reviewed，也不能支撑技法学习。

## standalone 环境文件污染根因修复

- clean standalone 完成普通及 OpenClaw E2E 后曾出现禁入成员 `.env`。根因不是构建器遗漏，而是 Next standalone 启动时把进程工作目录切换到制品目录；安全修复接口又以 `process.cwd()` 作为环境文件落点，因此测试和生产管理员调用均可能污染不可变 release，直到下次启动审计才暴露。

- 普通 standalone、blue/green slot 和两套 OpenClaw E2E 启动器均显式传递平台环境文件与物理 standalone 根。三套 Playwright 配置在运行前固定 release manifest 摘要，结束后拒绝 `.env*`、重新核对摘要并执行完整制品审计，形成 E2E 前后不可变性门禁。
