## LaunchAgent 受保护目录启动兼容

- 生产阻点位于 launchd 启动边界：旧 v2 plist 直接把受保护 Documents 仓库中的脚本作为 ProgramArguments 和 WorkingDirectory，Aqua LaunchAgent 在进入应用审计前被系统拒绝。应用 release、manifest、pending、数据库和 n8n 不因此失效，也不得通过跳过审计或改写旧授权绕过。
- 独立受管兼容安装器要求 canonical source 保持指定干净 Git commit，验证旧 installation、三个 plist、pinned Node、slot/router 脚本及停用状态后再执行。它备份并 CAS 替换三个 plist，把 WorkingDirectory 移到既有私有 supervisor 目录，并把极小 Node `process.execve` 启动逻辑直接绑定在 plist 摘要内；slot 仍运行原 start script 和完整 artifact audit，router 仍运行原 router script，两者保持 launchd PID。更新后的 v2 installation 正式记录三个新 plist 摘要、installer/启动逻辑/目标脚本来源，旧 manager 必须实际通过 preflight；失败自动恢复原安装。
- 该兼容层不修改 canonical 源码、OpenClaw 配置或插件、应用制品、release manifest、pending、receipt、路由状态、数据库或 n8n。它服务于已授权恢复，后续正式版本应把非受保护工作目录和 execve 启动合同纳入常规 installer/manager schema，而不是长期保留分叉恢复安装器。
- 标准安装路径随后复用同一纯 execve 合同模块：普通 installer 直接为 slot/router 生成 pinned Node `-e` ProgramArguments，并把 cwd 固定为 supervisor；仅当该目录落在用户 Documents、Desktop、Downloads 或 immutable release 内时拒绝，非受保护源码树的原 `.run` 默认仍兼容。v2 installation 新增共享模块、启动源码和 cwd 摘要，manager 每次 preflight/start/status 都验证该合同；恢复 adapter 也改为同一模块并绑定其独立 Git blob。这样常规重装不会重新生成受 TCC 保护的直接脚本启动方式，也没有引入第二套启动逻辑或新状态机。
- 新版 manager 不接受缺少 `manifest.execve` 的旧 v2 installation；升级顺序必须先运行同版本标准 installer `--apply`，再由同版本 manager preflight/start。当前不可变 3db pending 恢复继续使用原 3db manager 与已审兼容 installer，不能用新版 manager 替换旧恢复链；兼容测试明确从 3db Git blob加载旧 manager 做真实 preflight。
