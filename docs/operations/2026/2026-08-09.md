- 上午时段的会话元数据表现为一条用户输入后连续产生多轮 `exec` 工具调用和工具结果，其中包含直接媒体处理及状态检查行为；未发现实际调用 `submit-task.mjs`、`run-video-batch.mjs` 或正式平台状态查询。
- 没有证据表明版本化 `video-learning-pipeline` 入口被直接调用，但实际行为沿用了旧式临时处理思路：在 OpenClaw 会话内直接执行媒体命令并持续检查，而不是提交正式任务。会话同时出现上下文容量告警，密集工具轮次与阶段性播报共同放大了上下文压力。

### 根因结论

本次截图事故的可证根因不是 n8n 执行失败，而是任务根本没有提交到 n8n。OpenClaw 在原会话中走了临时命令、直接媒体处理和轮询旁路，形成多轮工具调用与重复进度播报，最终触发上下文容量问题。端口、Gateway 和模型服务在线不能推翻该结论，因为任务库与执行库在对应时段均没有正式链路活动。

正式流程统一为：

`User -> OpenClaw -> aiworker-task-flow -> Mission Control / SQLite -> n8n -> prepare -> Whisper audio + local Qwen vision -> finalize -> SQLite -> status query`

OpenClaw 每次只提交一次并立即返回异步回执；同一轮不得轮询，不得直接运行旧视频学习流程或临时媒体脚本。Whisper、Qwen 和最终工作节点均保持 `memoryMode=none`。

## 二次候选修复

### 候选设计

- 新增模块化 OpenClaw 原生插件，在 `qwen-current` Telegram 私聊消息进入模型前使用 `before_dispatch` 精确识别单行视频入口。命中后由 `execFile` 调用已安装的 `submit-task`，返回短异步回执并结束本轮 dispatch；其他消息明确放行，不改变原有对话路径。
- 插件生成稳定消息键、任务 ID 和幂等键，并把绝对视频入口作为一个不可展开的参数传给确定性脚本。脚本层同时保留解析 fallback，避免插件未命中时退回临时媒体处理；skill 继续作为模型说明和显式 CLI 后备层。
- 插件范围仅限 Telegram 私聊；群聊或缺少明确私聊分类的命令会短路拒绝。插件必须由 `qwen-current` 的非空 OpenClaw 插件 allowlist 明确启用，安装后还要核验插件 ID 已进入 allowlist。它不改变 Mission Control、n8n 工作流、模型路由、数据库 schema 或 `memoryMode=none` 约束。

### 上游行为核对

- 已从实际 `OpenClaw 2026.7.1-2` dispatch 代码确认：`before_dispatch` 会对普通消息全局调用，不依赖 channel binding；hook 返回 `handled` 后，运行时直接调用 `sendFinalPayload`，不会再进入模型生成。
- 该核对只证明候选 hook 位置与返回语义可用，不等于插件已被生产加载，也不等于单次提交、短回执或视频工作流已经验收通过。
