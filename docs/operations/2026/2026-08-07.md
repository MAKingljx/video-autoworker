### n8n 管道故障与修正

- 首次离线导入时，工作流列举达到 Node 默认约 4 GiB 堆上限；SQLite `quick_check` 正常，两个固定工作流 ID 均存在，n8n 服务在修正前保持离线。
- 根因是脚本将工作流 ID 列举直接接到 `grep -q`：第一个 ID 命中后匹配端提前关闭管道，n8n 继续输出第二个 ID 时收到 `EPIPE`，异常堆栈格式化随后持续消耗内存。独立列举命令在 1 秒内正常完成，排除数据库锁、损坏、SSH 中断和正常业务内存需求。
- 导入脚本现先完整收集 n8n 输出，再执行精确匹配，保留完整的上游退出状态。版本化运行配置同时为 CLI 和 LaunchAgent 提供可被外部环境覆盖的 8 GiB 堆上限作为生产余量；静态回归测试同时约束管道安全和安装模板，防止再次漂移。

### APFS 克隆兼容性修正

- 生产 Node `22.22.3` 对 `COPYFILE_FICLONE_FORCE` 返回 `ENOSYS`，但源目录与受控收件箱位于同一 APFS 卷，系统 `/bin/cp -c` 的独立 1 MiB 克隆探测通过。
- OpenClaw 提交脚本继续优先使用 Node 原生强制克隆；仅在 macOS 返回 `ENOSYS`、`ENOTSUP` 或 `EINVAL` 时，回退到系统 `/bin/cp -c -n`，并校验目标类型和字节数。其他错误仍立即失败，禁止静默退化为 7 GB 级完整复制。
- 整集首次启动还暴露出 APFS 克隆继承旧源文件修改时间的问题：prepare 前的 24 小时过期清理会把刚进入收件箱但 mtime 较旧的克隆误删。提交脚本现于克隆校验后把 atime/mtime 更新为实际收件时刻，再交由 n8n 接管。
- 技能规范现要求显式传入相同的 `--task-id` 与 `--idempotency-key`，避免 OpenClaw 只传幂等键时返回随机任务 ID，确保压缩或超时后只能查询同一任务。

## 多视频批次控制候选

### 需求与基线结论

- 新需求是让 OpenClaw 能安全提交多个视频，继续由 Whisper 分析语音、本地 Qwen 分析画面，并按模块化、组件化方式开发；模型工作节点仍不得参与长期记忆。
- 在完全独立的应用、n8n、数据库、媒体目录和批次目录中，用红、绿、蓝三个 12 秒测试视频复测旧版逐视频提交。三个任务均成功且结果未串片，但 n8n 执行时间分别为 `03:24:09.841-03:25:17.424`、`03:24:11.081-03:24:56.443`、`03:24:12.437-03:25:10.366`，证明不同工作流执行会重叠准备与 Whisper 作业。生产 Qwen 服务只有一个并行槽，因此直接并发提交大量长视频会造成 ffmpeg、Whisper、磁盘 I/O 和本地模型排队争用，旧方式不能作为可靠批量方案。

### 候选实现

- OpenClaw 技能拆分为回环平台客户端、受控媒体收件、单视频任务提交、批次状态与锁、批次后台执行器五类组件；单视频入口继续复用同一组件，不另建一套逻辑。
- 新增 `--video-dir`、`--batch-id`、`--batch-status`、`--resume-batch`。目录扫描不递归、排序固定、单批最多 100 个支持格式文件；批次命令立即返回，后台默认一次只处理一个视频，当前视频终态后才提交下一个。
- 批次 ID 和每个视频任务 ID 均稳定，状态以 0600 原子文件持久化并用进程锁防止重复控制器；重复批次直接返回既有状态，重启后只查询或续跑未完成项，不重复提交成功项。状态摘要不暴露源文件路径，也不把整批完整模型输出塞入 OpenClaw 会话。
- 安装脚本现在完整校验并原子安装 `scripts/` 与 `lib/` 组件；安装前备份和失败恢复逻辑继续保留。应用代码与 n8n 工作流没有变化。
