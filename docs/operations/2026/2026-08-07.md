### n8n 管道故障与修正

- 首次离线导入时，工作流列举达到 Node 默认约 4 GiB 堆上限；SQLite `quick_check` 正常，两个固定工作流 ID 均存在，n8n 服务在修正前保持离线。
- 根因是脚本将工作流 ID 列举直接接到 `grep -q`：第一个 ID 命中后匹配端提前关闭管道，n8n 继续输出第二个 ID 时收到 `EPIPE`，异常堆栈格式化随后持续消耗内存。独立列举命令在 1 秒内正常完成，排除数据库锁、损坏、SSH 中断和正常业务内存需求。
- 导入脚本现先完整收集 n8n 输出，再执行精确匹配，保留完整的上游退出状态。版本化运行配置同时为 CLI 和 LaunchAgent 提供可被外部环境覆盖的 8 GiB 堆上限作为生产余量；静态回归测试同时约束管道安全和安装模板，防止再次漂移。

### APFS 克隆兼容性修正

- 生产 Node `22.22.3` 对 `COPYFILE_FICLONE_FORCE` 返回 `ENOSYS`，但源目录与受控收件箱位于同一 APFS 卷，系统 `/bin/cp -c` 的独立 1 MiB 克隆探测通过。
- OpenClaw 提交脚本继续优先使用 Node 原生强制克隆；仅在 macOS 返回 `ENOSYS`、`ENOTSUP` 或 `EINVAL` 时，回退到系统 `/bin/cp -c -n`，并校验目标类型和字节数。其他错误仍立即失败，禁止静默退化为 7 GB 级完整复制。
