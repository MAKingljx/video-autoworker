## 真实 Telegram 状态查询误答

用户在已完成的视频任务之后发送自然语言状态询问。生产只读核验确认，目标父任务
及 `prepare`、`audio`、`vision`、`finalize` 四个阶段均在第一次执行中成功，阶段
输出和最终摘要均非空，n8n 只有一条成功的 video-analysis 执行，generic 工作流
没有增量，媒体工作目录已按任务范围清理。

当时用户消息使用了“再帮我查一下视频分析情况”这一口语表达。生产 `0.4.0`
状态语法没有把“视频分析情况”识别为状态意图；同一轮随后进入 Qwen，并调用
`memory_search` 读取到与该任务无关的旧 QA 记录，错误回复为“空 payload、模型
没有有效输出”，还重新提及已退役的视频处理方案。该回复不代表 Mission Control
或 n8n 的真实任务状态。

本记录只保留脱敏因果关系和结构化验证结论，不记录聊天正文、完整任务编号、发送者
标识、会话标识、绝对路径、原始日志或数据库内容。

## `0.4.1` 本地候选

`0.4.1` 只增加一个整句锚定的状态语法，识别“再帮我查一下视频分析情况”等受控
表达，并继续使用当前私聊受信的最近任务绑定。它不会把“不要查询”“怎么查询”
或示例文字当作状态读取，也不会接管视频编码、视频会议、订单等无关“情况”。

插件仍只注册一个 `before_dispatch`，没有模型工具；命中后只调用一次正式只读
状态客户端，提交调用为零，不轮询、不重试、不重提视频，也不把状态查询交给 Qwen、
记忆或文件搜索。版本同时写入 `package.json` 和 `openclaw.plugin.json`。

受控发布入口固定为已部署 `0.4.0` 到 `0.4.1`。它要求显式目标提交、canonical
main 与 GitHub main 一致、生产安装 payload 精确匹配已知 `0.4.0` 源；dry-run
只执行隔离官方安装。apply 只允许官方强制安装和刷新 `qwen-current`，配置必须逐字
保持不变，其他 OpenClaw profile、Mission Control、n8n 和共享模型监听必须保持
不变。任一安装、payload、索引、runtime、live Gateway、工具集合、配置或监听门
失败时，恢复完整 `0.4.0` payload 与配置，并保留唯一 active 恢复来源。

本地 Node 22 插件全套 22 个测试文件、331 项测试全部通过，包含成功升级、官方
候选安装失败、live 验证失败、active 来源重试成功和再次失败、显式回滚、回滚补偿、
受保护监听漂移和 Git 目标漂移。目标 ESLint、Node/Bash 语法及 `git diff --check`
通过。

本节截至提交前只表示本地候选通过，不冒充 GitHub 已发布、生产已升级或真实
Telegram 已验收。生产事实须在受控 apply 和用户新会话真实消息后追加。
